# SIM-on-FHIR

**Santeon CarePlan Implementation Guide** — beschrijft hoe het Santeon Informatie Model (SIM) wordt omgezet naar gestandaardiseerde HL7 FHIR R4-profielen.

## Publisher

[Santeon](https://www.santeon.nl) — FHIR versie: R4 (4.0.1)

---

## Getting started (Windows)

### 1. Clone the repository

```powershell
git clone https://github.com/SanteonNL/sim-on-fhir.git
cd sim-on-fhir
```

> **Line endings note:** The repo contains both `.bat` (Windows) and `.sh` (Unix) scripts. To avoid Git converting line endings and breaking the shell scripts, set this before cloning:
> ```powershell
> git config --global core.autocrlf input
> ```

### 2. Install prerequisites

| Tool | Purpose | Install |
|------|---------|---------|
| **Java** (JRE 11+) | Runs the HL7 FHIR IG Publisher | [adoptium.net](https://adoptium.net) |
| **Ruby + Devkit** | Required by the IG Publisher for Jekyll templating | [rubyinstaller.org](https://rubyinstaller.org/downloads/) — pick **Ruby+Devkit** |
| **Jekyll** | Processes IG templates into HTML | `gem install jekyll` (after Ruby) |
| **Python 3** | SQL mapping generator + local dev server | [python.org](https://www.python.org) — on Windows use `py -3` |
| **HL7 IG Publisher** (`publisher.jar`) | Builds the IG from FSH sources | Run `_updatePublisher.bat` (downloads ~100 MB) |

Verify each tool:
```powershell
java -version
ruby --version
jekyll --version
py --version
```

### 3. Install Jekyll on Windows

After installing Ruby via RubyInstaller, open a new PowerShell and run:

```powershell
ridk install 3      # installs MSYS2 + MINGW toolchain (needed for native gems)
ridk enable         # activates the toolchain in the current session
gem install jekyll
```

**If `gem install jekyll` fails due to a corporate proxy** (rubygems.org blocked), use MSYS2's package manager instead. Open the **MSYS2 UCRT64** terminal from the Start menu and run:

```bash
pacman -S mingw-w64-ucrt-x86_64-ruby
gem install jekyll bundler
```

Then add MSYS2 to your user PATH (no admin rights needed):

```powershell
[System.Environment]::SetEnvironmentVariable("PATH", $env:PATH + ";C:\msys64\ucrt64\bin", "User")
```

Close and reopen PowerShell, then verify with `jekyll --version`.

### 4. Download the IG Publisher

```bat
_updatePublisher.bat
```

Downloads `publisher.jar` (~100 MB) into `input-cache/`. Run this once on first setup, and again when you want to upgrade.

## Project Structure

```
sim-on-fhir/
├── input/
│   ├── fsh/
│   │   └── SanteonCarePlan.fsh         # FHIR profile (FSH source)
│   └── static/
│       ├── queries/
│       │   ├── luscii_careplan.sql      # LUSCII source query
│       │   └── pj_careplan.sql          # PJ source query
│       └── generate_fhir_sql_mappings.py  # Mapping generator script
├── input-cache/
│   └── publisher.jar                   # IG Publisher (not committed)
├── fsh-generated/                      # Auto-generated by publisher (do not edit)
├── output/                             # Built IG output (do not edit)

```

Key SQL source tables (LUSCII):
- `luscii_patients` — patient data
- `luscii_patientsprogramshistory` — enrollment timeline
- `luscii_programs` — program/category info
- `luscii_usersStatusChangeReasons` — status change tracking

## When you change a profile

### 1. Edit the FSH profile

Open [input/fsh/SanteonCarePlan.fsh](input/fsh/SanteonCarePlan.fsh) and make your changes.

### 2. Update SQL queries (if the data mapping changed)

Edit the relevant SQL file(s) in [input/static/queries/](input/static/queries/):
- `luscii_careplan.sql` — LUSCII data source
- `pj_careplan.sql` — PJ data source

### 3. Regenerate FSH mappings from SQL

Run the mapping generator to sync the `^mapping` statements in the FSH profile:

```bash
cd input/static
py generate_fhir_sql_mappings.py
```

This reads all `.sql` files in `queries/` and updates the mapping blocks in `SanteonCarePlan.fsh`.

### 4. Build the IG

From the repo root:

```bat
_genonce.bat
```

Build takes 1–3 minutes. Output goes to `output/`.

### 5. Preview locally

The IG pages use `fetch()`, so you need an HTTP server (not `file://`):

```bash
cd output
py -m http.server 8080
```

Then open `http://localhost:8080`.

## GitHub Pages branch previews

Every push and every pull request into `main` is built and published automatically by [.github/workflows/publish-ig.yml](.github/workflows/publish-ig.yml) — no local build needed to see how a branch looks.

The build result lands on the `gh-pages` branch, under a path that identifies where it came from:

| Trigger | Published at |
| --- | --- |
| Push to `main` | `https://santeonnl.github.io/sim-on-fhir/` |
| Push to another branch | `https://santeonnl.github.io/sim-on-fhir/<branch-name>/` |
| Pull request into `main` | `https://santeonnl.github.io/sim-on-fhir/pr-<number>/` |
| Manual run ([Actions tab](https://github.com/SanteonNL/sim-on-fhir/actions/workflows/publish-ig.yml) → *Run workflow*) | `https://santeonnl.github.io/sim-on-fhir/<keyword>/`, using the `keyword` input |

Progress and logs for any run are visible under the repo's [Actions tab](https://github.com/SanteonNL/sim-on-fhir/actions). Each branch/PR keeps its own folder on `gh-pages`, so multiple previews can exist side by side.

## Release process

Releases follow the same release-branch + release-candidate flow used across our repos, adapted here to publish a versioned IG build instead of compiled binaries. Every tag push is picked up automatically by [.github/workflows/publish-ig.yml](.github/workflows/publish-ig.yml) — nothing else needs to be triggered manually.

```text
main
 │
 ├── feature/x  ──┐
 ├── feature/y  ──┤  normal development
 ├── feature/z  ──┘
 │
 │   [feature-complete for 0.2.0]
 │
 ├── release/0.2.0
 │     ├─ tag v0.2.0-rc.1   → GitHub pre-release (automatic)
 │     ├─ fix: ...
 │     ├─ tag v0.2.0-rc.2   → GitHub pre-release (automatic)
 │     └─ tag v0.2.0        → GitHub release (automatic)
 │
 └── main  ←── merge back after release
```

### Step by step

**1. Create a release branch** once the features for this version are feature-complete. New work keeps going on `main` — it lands in the next version.

```bash
git checkout main
git pull
git checkout -b release/0.2.0
git push origin release/0.2.0
```

**2. Bump the version** in `sushi-config.yaml` (`version:`) to the target release version — e.g. `0.2.0` — and commit it on the release branch. The workflow's "Verify tag matches IG version" step fails the build if the tag and this value ever drift apart.

**3. Tag a release candidate** and push the tag:

```bash
git tag v0.2.0-rc.1
git push origin v0.2.0-rc.1
```

The workflow recognizes the `-rc.N` suffix and marks the GitHub Release as a **pre-release**.

**4. Fix bugs and tag new RCs** as needed, committing fixes on the release branch and tagging a new RC each time:

```bash
git commit -m "fix: correct age clamp boundary"
git tag v0.2.0-rc.2
git push origin v0.2.0-rc.2
```

**5. Tag the final release** once an RC is approved:

```bash
git tag v0.2.0
git push origin v0.2.0
```

This produces a full (non-pre-release) GitHub Release.

**6. Merge back to `main`**, then delete the release branch:

```bash
git checkout main
git merge release/0.2.0
git push origin main
```

### What the pipeline does on a tag push

| Step | What happens |
| --- | --- |
| **Verify version** | Fails fast if the tag's version doesn't match `sushi-config.yaml` |
| **Build** | Runs SUSHI + the HL7 IG Publisher, same as any other build |
| **Archive** | Zips the built `output/` site into `santeon-careplan-ig-<tag>.zip` |
| **Changelog** | Generated by GitHub's native release notes (one line per merged PR, contributors, compare link) |
| **GitHub Release** | Created with the zip attached and the correct pre-release flag |

Write clear PR titles — they go straight into the release notes.

### Versioning

Follows [Semantic Versioning](https://semver.org/):

```text
MAJOR.MINOR.PATCH

0.2.0
│ │ └── bugfix, backwards compatible
│ └──── new feature, backwards compatible
└────── breaking change
```

| Tag | Meaning |
| --- | --- |
| `v0.2.0-rc.1` | Release candidate 1 — under validation |
| `v0.2.0-rc.2` | Second RC after a fix |
| `v0.2.0` | Final release |

No `alpha`/`beta` tags — RC is sufficient for this workflow.

### Common mistakes

**Tagging the wrong branch** — the pipeline builds whatever commit the tag points to. Make sure you're on the release branch before tagging (`git log --oneline -5`, `git status`).

**Version already exists** — a tag can't be pushed again. If something went wrong: delete the tag locally and remotely, fix the issue, and push again.

```bash
git tag -d v0.2.0-rc.1
git push origin :refs/tags/v0.2.0-rc.1
```

_updatePublisher.bat
