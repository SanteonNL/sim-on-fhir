# SIM-on-FHIR

**SIM on FHIR Implementation Guide** — beschrijft hoe het Santeon Informatie Model (SIM) wordt omgezet naar gestandaardiseerde HL7 FHIR R4-profielen, met datasets per ziektebeeld en de-identificatie van exports.

## Publisher

[Santeon](https://www.santeon.nl) — FHIR versie: R4 (4.0.1)

---

## Getting started (Windows)

### 1. Clone the repository

```powershell
git clone https://github.com/SanteonNL/sim-on-fhir.git
cd sim-on-fhir
```

> **Line endings note:** The repo contains both `.bat` (Windows) and `.sh` (Unix) scripts. To avoid Git converting line endings and breaking the shell scripts, set this before cloning:
> ```powershell
> git config --global core.autocrlf input
> ```

### 2. Install prerequisites

| Tool | Purpose | Install |
|------|---------|---------|
| **Java** (JRE 11+) | Runs the HL7 FHIR IG Publisher | [adoptium.net](https://adoptium.net) |
| **Ruby + Devkit** | Required by the IG Publisher for Jekyll templating | [rubyinstaller.org](https://rubyinstaller.org/downloads/) — pick **Ruby+Devkit** |
| **Jekyll** | Processes IG templates into HTML | `gem install jekyll` (after Ruby) |
| **Python 3** | SQL mapping generator + local dev server | [python.org](https://www.python.org) — on Windows use `py -3` |
| **HL7 IG Publisher** (`publisher.jar`) | Builds the IG from FSH sources | Run `_updatePublisher.bat` (downloads ~100 MB) |

Verify each tool:
```powershell
java -version
ruby --version
jekyll --version
py --version
```

### 3. Install Jekyll on Windows

After installing Ruby via RubyInstaller, open a new PowerShell and run:

```powershell
ridk install 3      # installs MSYS2 + MINGW toolchain (needed for native gems)
ridk enable         # activates the toolchain in the current session
gem install jekyll
```

**If `gem install jekyll` fails due to a corporate proxy** (rubygems.org blocked), use MSYS2's package manager instead. Open the **MSYS2 UCRT64** terminal from the Start menu and run:

```bash
pacman -S mingw-w64-ucrt-x86_64-ruby
gem install jekyll bundler
```

Then add MSYS2 to your user PATH (no admin rights needed):

```powershell
[System.Environment]::SetEnvironmentVariable("PATH", $env:PATH + ";C:\msys64\ucrt64\bin", "User")
```

Close and reopen PowerShell, then verify with `jekyll --version`.

### 4. Download the IG Publisher

```bat
_updatePublisher.bat
```

Downloads `publisher.jar` (~100 MB) into `input-cache/`. Run this once on first setup, and again when you want to upgrade.

## Building the IG

Use the guarded build rather than calling the publisher directly:

```powershell
py -3 _buildIG.py            # with terminology server
py -3 _buildIG.py --no-tx    # without (faster, fewer checks)
```

The publisher does not report a failed Jekyll step: when it cannot render one resource it logs `Exception generating resource` and then waits for hours. `_buildIG.py` removes stale `temp/` and `output/`, reads the publisher log while it is written, stops at the first rendering exception, stops when Jekyll shows no progress, runs Jekyll itself to print the real error, and checks that `output/index.html` exists. The log is `ig-build.log`. CI uses the same script.

Run `sushi .` first and build straight after a merge, before making other changes: SUSHI does not find what the publisher finds.

## Folder layout and naming

Naming follows the HL7 Europe / EHDS conventions: logical models are `<Family><Name>` with the title "Name (model)"; FHIR profiles have the id `<resource>-san` (camelCase resource, family suffix) and the title "Resource (SAN)"; profiles generated per dataset are named `<Dataset><Resource>` with the id `<dataset>-<resource>` and the title "Resource (dataset)", for example `SbIbdObservation` / `sb-ibd-observation` / "Observation (sb-ibd)", and derive from the SAN profile.

```
input/fsh/
├── sim/               SIM logical models (SIMPatient, SIMVerrichting, ...) and the IBD dataset/cohort models
├── fhir/              FHIR profiles (ObservationSan, ProcedureSan, ...), extensions, concept maps
├── valuesets/         value sets
├── datasets/          one file per dataset (sb-ibd.fsh): cohort + the data requirements it releases
├── definitions/       ObservationDefinitions, data requirements, the definition models, external-definitions.yaml
├── deidentification/  de-identification ruleset model and standard ruleset
└── generated/         written by _generateFromDefinitions.py, never edited
```

## When you add or modify a SIM model or FHIR profile

Follow the same workflow when adding a new model or extending an existing one. For a new field, update the relevant existing files.

See [Modeling Workflow](docs/modelleerworkflow.md) for the modeling process, including SIM Logical Models, FHIR profiles, mappings, and semantic and technical delta analyses against Nictiz GBB.

```powershell
py -3 _generateFromDefinitions.py
sushi .
py -3 _buildIG.py --no-tx    # Fast build without terminology server
py -3 -m http.server 8080 -d output    # Preview at http://localhost:8080 (stop with Ctrl+C before the next build)
```

### Rules

- **Logical Model:** The SIM is the source of truth for definitions, datatypes, and cardinalities. Elements outside the current scope remain commented under `// Buiten IBD-scope - nog niet meegenomen`.
- **FHIR profile:** Constraints follow the SIM scope and FHIR R4 requirements. Additional restrictions must be explicitly justified.
- **Terminology:** Reuse existing SIM and Santeon terminology where applicable; harmonize with FHIR and Nictiz where necessary.
- **Open checks:** Document unresolved checks as `// TODO:` in the relevant FSH file.
- **Sources:** The SIM defines the information model; indicator definitions, `sb-ibd`, and HIPS ETL inform the dataset scope. FHIR R4 defines the technical representation.

If the field must also be exported, a dataset must ask for it in a data requirement; see the next section. The other way round: when a dataset asks for an element the SAN profile closes, the generator warns, and the element has to be modelled in the SAN profile first.

## When you change a data requirement, dataset or measurement definition

The profiles per dataset (sb-ibd, sb-copd, ...) are derived from definitions, not written per measurement. Edit the definitions in [input/fsh/definitions/](input/fsh/definitions/):

| File | Contains |
|------|----------|
| `ObservationDefinitions.fsh` | one ObservationDefinition per measurement (code, value type, unit, answers) |
| `ValueSets.fsh` | terminology for cohorts and coded answers |
| `DataRequirements.fsh` | data requirements (for a KPI, a questionnaire, ...): resource + FHIR search parameters + elements, post-query filters |
| `../datasets/<id>.fsh` | one file per dataset (in `input/fsh/datasets/`): cohort + the data requirements it releases |
| `DefinitionModels.fsh` | the `DataRequirementDefinition` / `DatasetDefinition` logical models |

ValueSets and Questionnaires maintained in ART-DECOR, on the NTS or on another FHIR server are not copied into the repository. They are registered in `external-definitions.yaml` with their `type`, `source` (`decor`, `nts` or `fhir`) and a pinned version, and referenced as `{vs:<key>}` or `{q:<key>}`:

```powershell
py -3 _syncDefinitions.py add <canonical-url> --key ibd-diagnosis     # register a ValueSet (ART-DECOR by default)
py -3 _syncDefinitions.py add <canonical-url> --type Questionnaire --key luscii-prems   # register a Questionnaire
py -3 _syncDefinitions.py add <canonical-url> --source nts --key ...   # from the NTS (NTS_USERNAME / NTS_PASSWORD)
py -3 _syncDefinitions.py fetch                                        # download the pinned versions (the build does this)
py -3 _syncDefinitions.py check                                        # is every pin still the latest? exit 1 when not
py -3 _syncDefinitions.py update                                       # move outdated pins, then regenerate
```

Content that cannot be downloaded (for example a SNOMED ECL query on the terminology server) is registered as `reference` and only resolved by the terminology server at validation time.

Then regenerate (needs SUSHI on the PATH):

```powershell
py -3 _generateFromDefinitions.py
```

This rewrites `input/fsh/generated/` (per dataset: profiles, code value sets, Groups, Parameters) and the dataset pages in `input/pagecontent/` (`datasets.md`, `<dataset-id>.md`). Commit the generated files; CI regenerates and fails when they are out of date. A new dataset also needs its page added under `datasets.md` in `sushi-config.yaml`. See the [Data requirements](input/pagecontent/data-requirements.md) page for how it works.

## GitHub Pages branch previews

Every push and every pull request into `main` is built and published automatically by [.github/workflows/publish-ig.yml](.github/workflows/publish-ig.yml) — no local build needed to see how a branch looks.

The build result lands on the `gh-pages` branch, under a path that identifies where it came from:

| Trigger | Published at |
| --- | --- |
| Push to `main` | `https://santeonnl.github.io/sim-on-fhir/` |
| Push to another branch | `https://santeonnl.github.io/sim-on-fhir/<branch-name>/` |
| Pull request into `main` | `https://santeonnl.github.io/sim-on-fhir/pr-<number>/` |
| Manual run ([Actions tab](https://github.com/SanteonNL/sim-on-fhir/actions/workflows/publish-ig.yml) → *Run workflow*) | `https://santeonnl.github.io/sim-on-fhir/<keyword>/`, using the `keyword` input |

Progress and logs for any run are visible under the repo's [Actions tab](https://github.com/SanteonNL/sim-on-fhir/actions). Each branch/PR keeps its own folder on `gh-pages`, so multiple previews can exist side by side.

## Release process

> Step-by-step guide in Dutch, including the quick local package: [docs/release.md](docs/release.md).

Releases follow the same release-branch + release-candidate flow as our GoReleaser repos (e.g. `fenix`), adapted to a FHIR IG instead of Go binaries. As with GoReleaser, **the git tag is the version**: [_release.py](_release.py) stamps it into `sushi-config.yaml` at build time (the IG equivalent of `-X main.version={{.Version}}`), so the FHIR package carries the exact tag version, and the release files get versioned names. Every tag push is picked up automatically by [.github/workflows/publish-ig.yml](.github/workflows/publish-ig.yml) — nothing else needs to be triggered manually.

```text
main
 │
 ├── feature/x  ──┐
 ├── feature/y  ──┤  normal development
 ├── feature/z  ──┘
 │
 │   [feature-complete for 0.2.0]
 │
 ├── release/0.2.0
 │     ├─ tag v0.2.0-rc.1   → GitHub pre-release (automatic)
 │     ├─ fix: ...
 │     ├─ tag v0.2.0-rc.2   → GitHub pre-release (automatic)
 │     └─ tag v0.2.0        → GitHub release (automatic)
 │
 └── main  ←── merge back after release
```

### Step by step

**1. Create a release branch** once the features for this version are feature-complete. New work keeps going on `main` — it lands in the next version.

```bash
git checkout main
git pull
git checkout -b release/0.2.0
git push origin release/0.2.0
```

**2. (Optional) Set the next base version** in `sushi-config.yaml` (`version:`), e.g. `0.3.0` on `main` after branching. It is only used for snapshot builds (`0.3.0-snapshot-<sha>`); tagged builds take their version from the tag, so there is no version bump to forget.

**3. Tag a release candidate** and push the tag:

```bash
git tag v0.2.0-rc.1
git push origin v0.2.0-rc.1
```

The workflow recognizes the `-rc.N` suffix and marks the GitHub Release as a **pre-release**.

**4. Fix bugs and tag new RCs** as needed, committing fixes on the release branch and tagging a new RC each time:

```bash
git commit -m "fix: correct age clamp boundary"
git tag v0.2.0-rc.2
git push origin v0.2.0-rc.2
```

**5. Tag the final release** once an RC is approved:

```bash
git tag v0.2.0
git push origin v0.2.0
```

This produces a full (non-pre-release) GitHub Release.

**6. Merge back to `main`**, then delete the release branch:

```bash
git checkout main
git merge release/0.2.0
git push origin main
```

### What the pipeline does on a tag push

| Step | What happens |
| --- | --- |
| **Stamp version** | `_release.py stamp` writes the tag's version (`v0.2.0-rc.1` → `0.2.0-rc.1`) and a matching `releaseLabel` into `sushi-config.yaml`; fails on a tag that is not `vX.Y.Z` or `vX.Y.Z-rc.N` |
| **Build** | Runs SUSHI + the HL7 IG Publisher, same as any other build |
| **Package** | `_release.py dist` writes `dist/` (see below) and checks the package version equals the tag |
| **Changelog** | Generated by GitHub's native release notes (one line per merged PR, contributors, compare link) |
| **GitHub Release** | Named `sim-on-fhir <tag>`, with the `dist/` files attached and the correct pre-release flag |

### Release files (`dist/`)

Like GoReleaser's `dist/`, every build (CI and local `_buildIG.py`) ends with:

| File | Contents |
| --- | --- |
| `santeon.sim-on-fhir-<version>.tgz` | The FHIR NPM package (`output/package.tgz`), with `<version>` in its `package.json` |
| `sim-on-fhir_<version>_site.zip` | The rendered IG website: the publisher's own `output/full-ig.zip`, renamed (zipped from `output/` only when that file is missing) |
| `checksums.txt` | SHA-256 of both files |

The version in the file name is read from the package itself, so the name always matches what is inside:

| Build | Version |
| --- | --- |
| tag `v0.2.0` | `0.2.0` (`releaseLabel: release`) |
| tag `v0.2.0-rc.1` | `0.2.0-rc.1` (`releaseLabel: release candidate`) |
| anything else (branch, PR, local) | `<base>-snapshot-<shortsha>` (`releaseLabel: ci-build`) — never mistaken for a release |

**Quick package without the site:** `py -3 _release.py pack` runs only SUSHI (about 30 s) and writes `dist/santeon.sim-on-fhir-<version>.tgz` + `checksums.txt` from `fsh-generated/resources`. It holds the differentials only (no snapshots, narratives or expansions, which the IG Publisher adds), add `--snapshot` to let SUSHI write the snapshots; use the full build for an official release.

Non-tag CI runs upload `dist/` as a workflow artifact (kept 14 days). Locally, `py -3 _release.py version` prints the version the current commit builds as; `_buildIG.py` stamps it for the build and restores `sushi-config.yaml` afterwards.

Write clear PR titles — they go straight into the release notes.

### Versioning

Follows [Semantic Versioning](https://semver.org/):

```text
MAJOR.MINOR.PATCH

0.2.0
│ │ └── bugfix, backwards compatible
│ └──── new feature, backwards compatible
└────── breaking change
```

| Tag | Meaning |
| --- | --- |
| `v0.2.0-rc.1` | Release candidate 1 — under validation |
| `v0.2.0-rc.2` | Second RC after a fix |
| `v0.2.0` | Final release |

No `alpha`/`beta` tags — RC is sufficient for this workflow.

### Common mistakes

**Tagging the wrong branch** — the pipeline builds whatever commit the tag points to. Make sure you're on the release branch before tagging (`git log --oneline -5`, `git status`).

**Version already exists** — a tag can't be pushed again. If something went wrong: delete the tag locally and remotely, fix the issue, and push again.

```bash
git tag -d v0.2.0-rc.1
git push origin :refs/tags/v0.2.0-rc.1
```
